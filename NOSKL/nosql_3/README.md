# Граф знань для рекомендаційної системи MovieLens 1M

## Мета роботи

Побудувати в Neo4j граф рекомендацій на реальному датасеті MovieLens 1M: перетворити початкові файли, спроєктувати property graph, виконати ідемпотентний пакетний імпорт, написати Cypher-запити, дослідити супервузли та застосувати PageRank, Louvain і Dijkstra з бібліотеки Graph Data Science (GDS).

## Структура проєкту

```text
nosql_3/
├── docker-compose.yml
├── convert.py
├── import/                     # UTF-8 CSV, згенеровані convert.py
├── queries/
│   ├── part2_load.cypher
│   ├── part3.cypher
│   ├── part4_supernodes.cypher
│   └── part5_gds.cypher
├── screenshots/                # результати власного запуску
└── README.md
```

## Запуск

1. Завантажити MovieLens 1M і розпакувати каталог `ml-1m` у корінь проєкту. Початкові файли мають кодування Latin-1 і роздільник `::`.
2. Конвертувати дані:

   ```powershell
   python convert.py --source ml-1m --output import
   ```

3. Запустити Neo4j із APOC та GDS:

   ```powershell
   docker compose up -d
   ```

4. Відкрити `http://localhost:7474`, увійти як `neo4j` / `password123` і послідовно виконати файли з `queries/`. Великі скрипти зручніше запускати через `cypher-shell`:

   ```powershell
   Get-Content -Raw queries/part2_load.cypher | docker exec -i neo4j_movielens cypher-shell -u neo4j -p password123
   ```

> Пароль у compose навчальний. У production його треба передавати через secret або змінну середовища. Початкові `.dat`, розпакований каталог і ZIP виключено з Git; згенеровані CSV залишаються частиною структури здачі.

## Частина 1 — проєктування схеми

```text
(:User {userId, gender, age, occupation, zip})
       │
       └──[:RATED {rating, timestamp}]──▶
                                      (:Movie {movieId, title, year})
                                               │
                                               └──[:HAS_GENRE]──▶(:Genre {name})
```

### Вузли та ребра

Вузлами стали довгоживучі сутності, які мають власну ідентичність і можуть бути самостійною точкою пошуку: `User`, `Movie`, `Genre`. Оцінка стала направленим ребром `RATED` від користувача до фільму. `rating` і `timestamp` описують саме факт взаємодії конкретної пари, тому є властивостями ребра. `HAS_GENRE` з'єднує фільм з одним або кількома жанрами.

### Чому Rating — ребро

У цьому датасеті одна оцінка належить одній парі користувач–фільм, не має інших зв'язків і потрібна переважно під час обходу від користувача до фільму. Ребро дає короткий природний патерн `(u)-[r:RATED]->(m)` і не додає мільйон проміжних вузлів. Окремий вузол `Rating` був би доречним, якби оцінка мала версії, коментарі, модерацію, джерела або інші власні зв'язки. Trade-off обраної моделі: Neo4j не підтримує звичайний uniqueness constraint для пари кінців ребра, тому ідемпотентність забезпечує `MERGE (u)-[r:RATED]->(m)`.

### Чому Genre — вузол, а не список

Окремий `Genre` робить жанр доступною точкою входу, дозволяє індексований пошук і природні обходи `User → Movie → Genre`, потрібні для рекомендацій та інтерпретації кластерів Louvain. Список у `Movie.genres` довелося б щоразу сканувати й розгортати; до жанру не можна було б додати метадані або інші зв'язки. Ціна нормалізації — додаткові `HAS_GENRE`, але в цьому наборі вона невелика й виправдана запитами.

## Частина 2 — завантаження

`convert.py` перевіряє кількість полів кожного рядка, читає Latin-1 та записує коректний UTF-8 CSV через стандартний модуль `csv`, тому коми й лапки в назвах фільмів екрануються автоматично. Поштовий індекс збережено: це наявна демографічна ознака, яку можна використати пізніше.

Перед імпортом створюються унікальні constraints для `User.userId`, `Movie.movieId` і `Genre.name`. Вони одночасно гарантують цілісність та створюють індекси для швидкого пошуку кінців зв'язків. Вузли імпортуються транзакціями по 1000 рядків, а оцінки через `apoc.periodic.iterate` батчами по 10 000. `parallel: false` уникає lock contention і deadlock під час конкурентного `MERGE`. Повторний запуск не створює дублів.

Фактичний імпорт повного MovieLens 1M: `6040` користувачів, `3883` фільми, `18` жанрів і `1000209` оцінок. APOC виконав `101` batch; `failedOperations = 0`.

## Частина 3 — шість запитів

Повний код міститься у `queries/part3.cypher`.

1. **Thriller з рейтингом понад 4.0.** Спочатку жанр обмежує множину фільмів, потім `avg()` і `count()` агрегують оцінки. Кількість оцінок показана поруч, бо середнє без розміру вибірки може вводити в оману.
2. **Користувачі з понад 50 п'ятизірковими оцінками.** `WHERE` фільтрує ребра до агрегації, `WITH` утворює групи за користувачем, а другий `WHERE` працює вже по `count()`.
3. **Спільні високо оцінені фільми користувачів 1 і 2.** Патерн сходиться в одному `Movie`, тому повертає лише справді спільні фільми без ручного self-join.
4. **Стабільно високо оцінені жанри.** Крім середнього повертається кількість оцінок; поріг `1000` прибирає нестійкі результати на малих вибірках.
5. **Collaborative filtering.** Схожість — кількість спільно високо оцінених фільмів. Після відбору 100 найближчих сусідів unseen-фільми ранжуються зваженою оцінкою. `NOT EXISTS` виключає вже оцінені цільовим користувачем фільми, а мінімум два peers зменшує випадковість.
6. **Найкоротший ланцюжок.** `shortestPath` шукає чергування `User–Movie–User`; межа шість ребер захищає від дорогого необмеженого обходу щільного графа.

Довжина шляху — кількість пройдених ребер `RATED`. Довжина 2 означає, що два користувачі оцінили спільний фільм: `User–Movie–User`. Довжина 4 означає зв'язок через одного проміжного користувача і два фільми. Довжина 6 — через двох проміжних користувачів і три фільми. Це не соціальна близькість у буквальному сенсі: низька оцінка теж створює ребро, тому для смакової близькості краще обмежувати `rating >= 4` або користуватися зваженим `SIMILAR`.

## Частина 4 — супервузли

`part4_supernodes.cypher` спочатку ранжує всі вузли за degree, а потім рахує середнє, p95, p99 і максимум окремо для кожного label. Так супервузол визначається відносно розподілу, а не довільним числом. На повному MovieLens головний супервузол — `American Beauty (1999)` з degree `3430` (`3428` оцінок). Далі йдуть `Star Wars: Episode V` та `Episode IV` з degree `2995`. Серед користувачів найбільший degree має `User 4169` — `2314`. Для Movie середній degree дорівнює `259.24`, p99 — `1759.58`, максимум — `3430`; PROFILE популярного фільму показав `18055 db hits`.

Супервузол повільніший не через відсутність індексу: індекс швидко знаходить стартовий вузол, але після цього `Expand` все одно мусить прочитати кожне суміжне ребро, створити багато проміжних рядків і часто виконати агрегацію або сортування. Це видно у `PROFILE` за `db hits` і `rows` на операторах Expand.

Конкретна стратегія для цього датасету — фільтрувати ребра якомога раніше (`rating >= 4`), обмежувати кандидатів і матеріалізувати зважені `SIMILAR` лише для найсильніших 50 000 пар. Для повторюваних агрегатів популярності можна періодично зберігати `ratingCount` і `avgRating` на `Movie`. Розбиття популярного фільму на штучні вузли-бакети тут погіршило б прості запити, тому його варто застосовувати лише при доведеній проблемі запису/блокувань.

## Частина 5 — GDS

### PageRank

Проєкція містить `User`, `Movie` та направлені `RATED`. Оскільки всі голоси йдуть до фільмів, PageRank ранжує структурну популярність. У цій моделі оцінка ребра не використовується, тому результат радше відображає кількість/авторитетність оцінювачів, а не якість фільму. Перевірка інтерпретації: зіставити топ PageRank із `count(r)` та `avg(r.rating)`.

### Louvain

Пари користувачів з'єднуються `SIMILAR`, якщо мають щонайменше три спільні фільми з оцінкою не нижче 4; вага дорівнює числу таких фільмів. Через квадратичну кількість можливих пар залишаються 50 000 найсильніших зв'язків. Louvain записує `communityId`, після чого для десяти найбільших спільнот обчислюються три найпопулярніші жанри.

Кластери можна називати «любителями бойовиків» чи «поціновувачами артхаусу» лише після перевірки: порівняти top-3 жанри та їх частки між спільнотами, переглянути характерні фільми й демографію. Сам communityId семантики не має. Окремі ізольовані користувачі та обмеження top-50 000 також впливають на розмір кластерів.

### Dijkstra

Для Dijkstra сила схожості перетворена на вартість `cost = 1 / weight`, адже алгоритм мінімізує суму. Інакше сильні зв'язки парадоксально були б «дорогими». Для кількох пар треба записати `hops`, проміжні userId і середнє. Гіпотеза «шести рукостискань» тут перевіряється лише на проєкції top-50 000 схожостей, а не на людських знайомствах; недосяжна пара означає різні компоненти проєкції, а не відсутність зв'язку у вихідних рейтингах.

### Фактичні результати

На повному датасеті PageRank поставив на перше місце American Beauty (1999) (score 5.4219), далі Star Wars: Episode VI (3.9579), Episode IV (3.9234) та Episode V (3.6694). Це узгоджується з їхнім високим degree і підтверджує, що в цій проєкції PageRank насамперед вимірює популярність.

Louvain отримав 4824 спільноти з modularity 0.1550. Чотири найбільші мають 750, 225, 177 і 68 користувачів; велика кількість singleton-кластерів є наслідком обмеження до 50 000 найсильніших пар. У найбільшій спільноті top-3: Drama (62961), Comedy (51646), Action (35499). Абсолютні top-жанри великих кластерів схожі, тому для семантичних назв варто порівнювати нормалізовані частки та характерні фільми.

Користувачі 1 і 2 не мають шляху у розрідженій similarity-проєкції. Для зв'язаної пари 17 і 18 Dijkstra знайшов шлях [17, 4277, 18]: 2 hops, total cost 0.013425. Це тісний світ у межах найбільшої компоненти, але не доказ шести рукостискань для всіх 6040 користувачів.

## Частина 6 — аналіз і висновки

### Граф vs SQL

Запити 1–4 нормально реалізуються в SQL, часто навіть ефективніше для великих агрегацій. Перевага графа стає очевидною у запитах 5 і 6: рекомендація читається як послідовність локальних обходів, а змінна довжина шляху є частиною мови. SQL-еквівалент базової рекомендації вимагав би щонайменше двох self-join таблиці ratings, anti-join для переглянутих фільмів, кількох GROUP BY і ранжування. Для довільного найкоротшого шляху потрібен рекурсивний CTE з масивом відвіданих вузлів, контролем циклів і окремим вибором мінімальної глибини; це можливо в сучасному PostgreSQL, але значно довше, складніше для підтримки й менш природно оптимізується як обхід.

```sql
-- Скорочений SQL-аналог пошуку спільно вподобаних фільмів
SELECT r1.movie_id, COUNT(*) AS common_likes
FROM ratings r1
JOIN ratings r2 ON r2.movie_id = r1.movie_id
WHERE r1.user_id = 1 AND r2.user_id <> 1
  AND r1.rating >= 4 AND r2.rating >= 4
GROUP BY r1.movie_id;
```

### Де граф програє

Реляційна або колонкова система краще підходить для глобальних звітів: середня оцінка за роками, розподіл оцінок за віком, експорт усіх ratings, OLAP-зрізи й масове завантаження. Такі операції сканують значну частину таблиці та мало використовують топологію. SQL також має зрілу декларативну схему, простіші constraints для складених ключів `(user_id, movie_id)` і звичніший стек BI. Практична production-архітектура може залишати факти оцінок у SQL/warehouse, а Neo4j використовувати як спеціалізовану проєкцію для online traversals і рекомендацій.

### Покращення схеми

Для запиту 1 можна матеріалізувати на `Movie` властивості `ratingCount` і `avgRating`, оновлюючи їх пакетно: тоді відпаде обхід усіх `RATED`. Це денормалізація, тому потрібна контрольована процедура оновлення. Для запиту 5 доцільно матеріалізувати `SIMILAR {weight, cost, calculatedAt}` за розкладом і зберігати лише top-K сусідів для кожного користувача; online-запит стане коротким обходом, а не дорогим self-join графа оцінок. Для часових рекомендацій можна додати decay до ваги за `timestamp`. Водночас не варто перетворювати кожну оцінку на вузол без нових вимог: це збільшить граф і довжину всіх основних шляхів.

## Підсумок

Графова модель особливо вдала там, де цінність міститься у зв'язках: пошук схожих користувачів, багатокрокові рекомендації, спільноти та маршрути. Вона не замінює SQL для всіх задач. Найкращий результат дають query-first схема, раннє обмеження обходу, індексовані стартові вузли, контроль супервузлів і свідоме матеріалізування дорогих похідних зв'язків.
